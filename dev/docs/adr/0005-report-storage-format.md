# ADR-0005: レポート保存形式（Markdown + Front Matter）

- 日付: 2025-11-22
- ステータス: 承認
- レイヤ: core / infrastructure
- 種別: データストア
- 関連コンポーネント: core.models.Report, infrastructure.git.repo_writer

---

## 1. 背景 / コンテキスト

Kamojiros では、エージェントや人間が作成した知識（Report）を永続化する必要があります。
検索性、可読性、ポータビリティを考慮した保存形式を決める必要があります。

- 目的・解決したいこと:
  - 人間がテキストエディタでそのまま読める形式にしたい。
  - メタデータ（作成日、タグ、著者など）を構造化して持ちたい。
  - 特定の DB 製品にロックインされたくない。

- 前提・制約:
  - Git でバージョン管理する。
  - 静的サイトジェネレータ（MkDocs）で公開する。

---

## 2. 決定

**Markdown ファイル + YAML Front Matter** を正本データとして採用します。
ファイルパスは `docs/journal/YYYY/MM/DD/{note_id}.md` とします。
データベース（Postgres 等）は、あくまで検索や集計のための「インデックス / キャッシュ」として扱い、正本とはしません。

---

## 3. 選択肢と評価

### 採用案（Markdown + Front Matter）

- 概要:
  - 本文は Markdown。
  - メタデータはファイルの先頭に YAML 形式で埋め込む（Jekyll / Hugo / MkDocs 互換）。
- メリット:
  - **可読性**: エディタや GitHub/GitLab 上でそのまま読める。
  - **ツール互換性**: 多くの静的サイトジェネレータや Obsidian などのノートアプリでサポートされている。
  - **ポータビリティ**: テキストファイルなのでどこへでも移行しやすい。
- デメリット:
  - メタデータの更新（リネームやタグ変更）が全ファイル走査になるため、DB に比べて遅い（ただし数万ファイル程度なら問題ない）。

### 代替案 A (JSON / YAML ファイル)

- 概要: 全体を JSON や YAML で保存し、`body` フィールドに Markdown を入れる。
- 採用しなかった理由:
  - Markdown としての可読性が下がる（改行のエスケープなど）。
  - エディタでのプレビューが効きにくい。

### 代替案 B (Database Only)

- 概要: SQLite や Postgres にのみ保存し、ファイルには書き出さない。
- 採用しなかった理由:
  - Git でのバージョン管理や差分確認が難しくなる。
  - 「GitLab Pages で公開する」というホスティング戦略と矛盾する。

---

## 4. 根拠（評価軸と判断）

- **Human-Readable**: 「人間が直接読めること」を重視しました。システムが壊れてもテキストファイルさえあれば知識は失われません。
- **GitOps**: レポートの追加・修正を Git のコミットとして扱えるため、レビューや履歴管理のフローが開発プロセスと統合できます。

---

## 5. 影響範囲

- **Core**:
  - `Report` モデルは `meta` と `body_markdown` を持つ構造になる。
- **Infrastructure**:
  - `MarkdownReportRepository` は、`Report` オブジェクトと Markdown ファイルの相互変換（シリアライズ/デシリアライズ）を担う。
- **File System**:
  - `docs/journal/YYYY/MM/DD/` というディレクトリ階層が強制される。

---

## 6. ロールアウト / 移行方針

- フェーズ1（完了）:
  - `MarkdownReportRepository` の実装。
  - `Report` モデルの定義。
- フェーズ2:
  - 既存の Markdown ファイルがある場合、Front Matter のスキーマに合わせて変換するスクリプトが必要になる可能性がある。

---

## 7. オープンな論点 / フォローアップ

- **Front Matter Schema**: 必須フィールド（`note_id`, `created_at` 等）とオプションフィールド（`tags`, `score` 等）の厳密な定義。Pydantic モデルと同期させる必要がある。
- **ファイル名**: 現状は `{note_id}.md` だが、人間がファイル名だけで内容を判別できるように `{date}-{slug}.md` のような形式にするか検討中（ADR 上は `note_id` ベースで実装済みだが、変更の余地あり）。
