# ADR-0028: LLM Retry and Fallback Strategy

- 日付: 2025-12-14
- ステータス: 承認
- レイヤ: infrastructure
- 種別: エージェント統合 / 運用フロー
- 関連コンポーネント: infrastructure.genai.pydantic_ai_factory

---

## 1. 背景 / コンテキスト

この ADR で「何を」「なぜ」決めるのかを、プロジェクト文脈で書く。

- 目的・解決したいこと:
  - 外部の大規模言語モデル（LLM）API呼び出しの信頼性と安定性を向上させたい。特に、Google Gemini API (AI Studio) 利用時に頻繁に発生するレート制限（HTTP 429 Too Many Requests）に対して、インテリジェントに対応し、無駄な試行を減らしつつ、サービス断を最小限に抑える必要がある。
- 前提・制約:
  - `pydantic-ai` ライブラリを介して LLM を利用している。
  - 主に Google の Gemini モデル（AI Studio版とVertex AI版）を利用する。
  - AI Studio は、特に無料枠において厳しいレート制限が課せられる可能性がある。

---

## 2. 決定

LLM API呼び出しの安定性向上のため、`tenacity` ライブラリを活用した高度なリトライ戦略と、モデルの特性に応じたフォールバック戦略を導入する。

- **リトライ戦略**:
  - `pydantic-ai-slim[retries]` 依存関係を追加し、`tenacity` を利用する。
  - HTTPステータスコード `429 (Too Many Requests)` のエラーレスポンスボディを解析し、日次クォータ（"PerDay" を含むエラー）が原因の場合は回復が見込めないためリトライ**しない**。
  - 分次（RPM/TPM）など、時間経過で回復可能な `429` エラーや、一時的なサーバーエラー（`502`, `503`, `504`）はリトライ対象とする。
  - 待機時間は、APIレスポンスに含まれる `RetryInfo.retryDelay` の値を優先的に使用する。それが存在しない場合は、exponential backoff 戦略で待機する。

- **フォールバック戦略**:
  - `gemini-2.5-pro` モデルは、常に安定したパフォーマンスが期待できる Vertex AI を使用する。
  - `gemini-2.5-flash` モデルは、AI Studio の API キーが設定されている場合、上記のリトライ戦略を適用した上で AI Studio を優先的に使用する。API キーがない場合は Vertex AI にフォールバックする。

- **実装**:
  - これらのロジックを `httpx.AsyncClient` と `pydantic_ai.retries.AsyncTenacityTransport` を用いてカプセル化し、`pydantic-ai` の `GoogleProvider` に注入する。
  - 作成したHTTPクライアントは `lru_cache` を用いてインスタンスを再利用し、効率化を図る。

---

## 3. 選択肢と評価

検討した選択肢と、その評価を軽くまとめる。

### 採用案（本 ADR の決定）

- 概要:
  - `tenacity` による、エラー内容を判別するインテリジェントなリトライと、API推奨の待機時間を尊重する戦略。
- メリット:
  - 日次クォータ超過のような回復不能なエラーでの無駄なリトライを回避できる。
  - API の挙動に合わせた効率的で行儀の良いリトライが可能になる。
  - `pydantic-ai` の `GoogleProvider` に注入する形で実装するため、この Provider を利用するすべてのエージェントが一貫した恩恵を受けられる。
  - 安定性を求める `pro` モデルと、コスト効率を重視する `flash` モデルで、最適なバックエンドを使い分けることができる。
- デメリット / リスク:
  - Gemini API のエラーレスポンス形式の変更に追従する必要があり、将来的なメンテナンスコストが発生する可能性がある。

### 代替案 A: 単純なリトライ

- 概要:
  - エラーの種類を問わず、固定回数・固定間隔、あるいは単純な exponential backoff でリトライする。
- 採用しなかった理由:
  - 日次クォータ超過時に無駄なリトライを繰り返し、リソースを浪費してしまう。
  - API が推奨する待機時間を無視するため、最適なタイミングでリトライできず、回復が遅れる可能性がある。

---

## 4. 根拠（評価軸と判断）

どんな観点で比較して、この決定になったかを書く。

- ビジョンとの整合:
  - システムの堅牢性と信頼性を高めるという方針に合致する。手動でのリトライやエラー対応の手間を減らし、自律的な運用を目指す。
- 非機能要件:
  - **信頼性**: 外部APIの一時的な障害やレート制限に対する耐性が大幅に向上する。
  - **効率性**: 回復不能なエラーを即座に失敗させることで、不要な待機時間とリソース消費を削減する。
- チーム / 自分のスキル・運用コスト:
  - `tenacity` はデコレータベースで宣言的にリトライロジックを記述できるため、可読性が高く、導入コストが低い。

## 5. 影響範囲

この決定が影響するものを列挙する。

- コード / ディレクトリ構成:
  - `src/kamojiros/infrastructure/genai/pydantic_ai_factory.py` が主要な変更箇所となる。
  - `pyproject.toml` と `uv.lock` に `pydantic-ai-slim[retries]` と `tenacity` が追加される。
- 既存・将来のコンポーネント:
  - `create_pydantic_ai_model` ファクトリ関数を利用して LLM をインスタンス化するすべてのサービス（例: `QAService`, `DeepResearchService`）が、このリトライ・フォールバック戦略の対象となる。

---

## 6. ロールアウト / 移行方針

- 既に実装済み。
- `pydantic_ai_factory` を経由する既存のLLM利用箇所は、自動的にこの新しい戦略の恩恵を受ける。

---

## 7. オープンな論点 / フォローアップ

- open question:
  - `tenacity` の試行回数（`stop_after_attempt(5)`）や最大待機時間（`min(sec, 60.0)`）などのパラメータは、今後の運用実績を見ながら調整する可能性がある。
  - Gemini 以外のLLM（例: Anthropic Claude）を導入する場合、同様のリトライ戦略を別途実装する必要がある。
