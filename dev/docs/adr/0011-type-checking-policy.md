# ADR-0011: 型チェック方針 (Pyright / Strict)

- 日付: 2025-11-22
- ステータス: 承認
- レイヤ: dev-experience
- 種別: 開発プロセス
- 関連コンポーネント: pyproject.toml

---

## 1. 背景 / コンテキスト

Python は動的型付け言語ですが、大規模なコードベースや堅牢性が求められるエージェント開発においては、静的型チェックが不可欠です。
どのツールを使い、どの程度の厳格さで運用するかを決める必要があります。

---

## 2. 決定

**Pyright** を採用し、可能な限り **Strict モード** に近い設定で運用します。
`mypy` ではなく `pyright` をメインの型チェッカーとします。

- **Tool**: Pyright
- **Severity**: エラーを許容しない（CI で落とす）。
- **Type Hints**: すべての関数シグネチャに型ヒントを必須とする。

---

## 3. 選択肢と評価

### 採用案 (Pyright)

- メリット:
  - **速度**: Mypy より高速。
  - **VS Code 統合**: Pylance のベースであり、エディタ上の表示と CLI の結果が一致しやすい。
  - **推論能力**: 優秀な型推論を持つ。
- デメリット:
  - Mypy プラグイン（Pydantic plugin 等）のエコシステムが使えない場合がある（ただし Pydantic v2 は標準の型ヒントで十分動作する）。

### 代替案 A (Mypy)

- 概要: Python の標準的な型チェッカー。
- 採用しなかった理由:
  - 遅い。
  - 設定が複雑になりがち。

---

## 4. 根拠（評価軸と判断）

- **Developer Experience**: VS Code での開発が主であるため、エディタとの親和性を最優先しました。
- **Modern Python**: Pydantic v2 との相性が良く、最新の Python の型機能への追随も早いため。

---

## 5. 影響範囲

- **Codebase**: `Any` の使用を極力避ける。ジェネリクスを適切に使う。
- **CI**: `pyright` コマンドを実行。
