# ADR-0012: テストフレームワーク (pytest + nox)

- 日付: 2025-11-22
- ステータス: 承認
- レイヤ: dev-experience
- 種別: テスト
- 関連コンポーネント: noxfile.py, tests/

---

## 1. 背景 / コンテキスト

テストの実行、および複数の Python バージョンや環境（lint, typecheck）でのタスク実行を自動化・標準化する必要があります。

---

## 2. 決定

- **Test Runner**: **pytest** を採用します。
  - 最も普及しており、フィクスチャやプラグインが豊富。
- **Task Runner**: **nox** を採用します。
  - `tox` よりも Python コードで設定を書けるため柔軟性が高い。
  - `uv` バックエンドを使用して高速化する。

---

## 3. 選択肢と評価

### 採用案 (pytest + nox)

- メリット:
  - **pytest**: 簡潔なアサーション、強力なフィクスチャ。
  - **nox**: 仮想環境の分離が容易。CI 上のステップをローカルで再現しやすい。
- デメリット:
  - nox の学習コストが少しある（tox に慣れている場合）。

### 代替案 A (unittest + Makefile)

- 概要: 標準ライブラリのみで構成。
- 採用しなかった理由:
  - ボイラープレートが多い。
  - クロスプラットフォームなタスク実行が難しい。

---

## 4. 根拠（評価軸と判断）

- **Reproducibility**: CI とローカルで全く同じコマンド（`nox -s test` 等）でテストできることを重視しました。
- **Flexibility**: noxfile.py は Python スクリプトなので、複雑なセットアップ処理も記述可能です。

---

## 5. 影響範囲

- **CI**: `.gitlab-ci.yml` は `nox` を呼び出すだけで済むようになる。
- **Local**: 開発者は `nox` コマンドでテストやリンターを実行する。
