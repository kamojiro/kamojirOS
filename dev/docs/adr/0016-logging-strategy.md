# ADR-0016: ログ出力戦略 (Standard Logging)

- 日付: 2025-11-22
- ステータス: 承認
- レイヤ: infrastructure
- 種別: 観測可能性
- 関連コンポーネント: src/kamojiros/utils/logging.py (仮)

---

## 1. 背景 / コンテキスト

アプリケーションの動作状況を把握し、トラブルシューティングを行うためにログ出力が必要です。
ライブラリ依存を増やしすぎず、かつ扱いやすいログ基盤が必要です。

---

## 2. 決定

Python 標準の **logging** モジュールを使用します。
ただし、開発時の可読性を高めるために、ハンドラとして **Rich** を使用することを推奨します（必須ではない）。

- **Format**: JSON (本番/ファイル出力), Colored Text (開発時コンソール)。
- **Level**: 環境変数で制御可能にする。

---

## 3. 選択肢と評価

### 採用案 (Standard Logging + Rich Handler)

- メリット:
  - **標準準拠**: ライブラリ作者としてもアプリケーション開発者としても、標準 `logging` を使うのが最も互換性が高い。
  - **Rich**: コンソール出力が見やすい。
- デメリット:
  - `structlog` ほど構造化ログが強力ではない（が、標準でも JSON Formatter を入れれば十分）。

### 代替案 A (Loguru)

- 概要: API が使いやすいサードパーティライブラリ。
- 採用しなかった理由:
  - 標準 `logging` との相互運用性（ライブラリからのログを拾うなど）に一手間かかる場合がある。
  - 独自のお作法が強い。

---

## 4. 根拠（評価軸と判断）

- **Compatibility**: 外部ライブラリ（Pydantic AI, HTTPX 等）が出すログも統一的に扱いたいため、標準 `logging` をベースにするのが安全です。
- **Simplicity**: 過度な抽象化を避けるため。

---

## 5. 影響範囲

- **Codebase**: `logger = logging.getLogger(__name__)` パターンを徹底する。
- **Config**: アプリケーション起動時に `logging.config.dictConfig` 等で設定を初期化する。
