# ADR-0007: 検索インデックス戦略（Activity / Notes 分離）

- 日付: 2025-11-22
- ステータス: 提案中
- レイヤ: infrastructure
- 種別: データストア / 検索
- 関連コンポーネント: infrastructure.vector_store

---

## 1. 背景 / コンテキスト

エージェントが過去の情報を参照したり、新しいテーマを発見したりするためには、蓄積されたデータを検索可能にする必要があります。
特に「最近の話題（Activity）」と「蓄積された知識（Report/Note）」は性質が異なるため、適切なインデックス戦略が必要です。

- 目的・解決したいこと:
  - 「最近何に興味を持っていたか」を検索したい（短期記憶的）。
  - 「過去にどんなことを調べたか」を検索したい（長期記憶的）。
  - 検索ノイズを減らしたい。

---

## 2. 決定

ベクトル検索インデックスを以下の 2 つに分離して管理します。

1.  **activity_index**:
    - 対象: Misskey のノート、Discord のログ、Web 閲覧履歴などの `Activity`。
    - 性質: フロー情報。短期的・雑多。量が多い。
    - 用途: Theme Generator が「最近の興味」を抽出するために使う。
2.  **notes_index**:
    - 対象: `docs/` 配下の `Report` (journal, notes)。
    - 性質: ストック情報。長期的・体系的。質が高い。
    - 用途: Report Generator が「過去の知識」を参照するために使う。

---

## 3. 選択肢と評価

### 採用案（インデックス分離）

- メリット:
  - **検索精度の向上**: 質の高い知識（Notes）と雑多なログ（Activity）を混ぜずに検索できるため、RAG の回答精度が上がる。
  - **ライフサイクル管理**: Activity は古いものを捨てたりアーカイブしたりしやすい。Notes は永続的に保持する。
- デメリット:
  - 2つのインデックスを管理する手間が増える。

### 代替案 A (単一インデックス + メタデータフィルタ)

- 概要: すべて同じインデックスに入れ、`type: activity` / `type: report` でフィルタする。
- 採用しなかった理由:
  - データ量のオーダーが違う（Activity >>> Report）ため、インデックスが肥大化し、検索パフォーマンスやコストに悪影響が出る恐れがある。
  - ベクトル空間内での意味の混在（「つぶやき」と「論文要約」が近くに来るなど）がノイズになる可能性がある。

---

## 4. 根拠（評価軸と判断）

- **データの性質**: フロー情報とストック情報は明確に分けるべきという設計思想に基づきました。
- **エージェントの役割**:
  - `ThemeGenerator` は「雑多なログから兆しを見つける」のが仕事 → `activity_index`
  - `ReportGenerator` は「確かな知識に基づいて執筆する」のが仕事 → `notes_index`
  という役割分担に対応しています。

---

## 5. 影響範囲

- **Infrastructure**: ベクトルストアの実装において、コレクション（テーブル）を分ける必要がある。
- **Apps**: 各エージェントは、目的に応じてどちらのインデックスを使うか（あるいは両方使うか）を選択する。

---

## 6. ロールアウト / 移行方針

- フェーズ3（予定）:
  - ベクトルストア（Supabase pgvector 等）の導入時に、最初からテーブルを分けて作成する。
  - 同期バッチもそれぞれ別に実装する。

---

## 7. オープンな論点 / フォローアップ

- **Activity の保存期間**: `activity_index` は無限に肥大化するため、TTL（Time To Live）を設定するか、古いものをアーカイブする仕組みが必要。
- **Unified Search**: 人間が検索するときは両方を横断検索したい場合がある。そのための API ラッパーが必要になるかもしれない。
